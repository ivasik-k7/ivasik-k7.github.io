# 2. Existing Performance Context

A previous production performance audit has already identified several important issues.

Use these findings as **baseline evidence**, not as the entirety of the audit.

## Previously confirmed boot problem

Production build:

* `createAnimal`: ~1,433 ms across 5 calls
* `createNpc`: ~376 ms across 18 calls
* approximately 1.8 s of sprite-rig construction
* approximately 2,009 ms module-evaluation long frame
* 1,125 sprite frames
* ~1,078,896 cells constructed during boot

Root cause:

* module-scope eager enumeration of NPC/animal registries;
* developer-only studios imported statically;
* dev tooling forcing production-time asset/rigger construction.

A fix has already been implemented:

* lazy NPC/animal registries;
* cached lazy rig construction;
* developer studios loaded through `React.lazy`.

Measured result:

* `EngineGame` chunk: 876 KB → ~572 KB
* studios split into separate chunks
* longest blocking frame: ~2,009 ms → ~777–1,060 ms
* FCP: ~2.8–4.9 s → ~1.3–1.9 s

This was not a controlled A/B benchmark, so treat the exact delta cautiously, but the mechanism has been confirmed.

## Other confirmed performance findings

### District DOM explosion

District currently mounts approximately:

* 7,785 hidden `<rect>` elements;
* approximately 9,377 total DOM nodes;
* thousands of sprite-frame elements that are never displayed.

An A/B experiment showed:

* mounting only `idleFrame` + `walkCycle`
* DOM reduction ~75%
* rectangle reduction ~81%
* district scene entry approximately 1,031 ms → 220 ms

This is considered a high-confidence optimization.

### Per-NPC React animation

NPCs currently use per-NPC `setInterval` + React state for animation.

Measured while standing still:

* ~1,000–1,600 `<rect>` elements reconstructed per second;
* ~23–32 React commits/sec in NPC-heavy scenes;
* significant DOM mutation churn.

The intended architectural direction is to move animation advancement away from React state and onto the existing game/atlas/rAF rendering path.

### Full-rate processing behind menus

NPC animation and monologues continue running while a fullscreen menu is open.

An existing `playing` prop can potentially be used to suspend visual updates.

### Monologue layout thrashing

`NpcMonologue` performs layout reads such as `offsetWidth` for individual typed characters.

Measured:

* approximately 853 ms of forced layout over 20 seconds in District.

This is compounded by the excessive District DOM.

### Dead assets

Two declared webfonts are never actually applied and produce approximately 157 KB of dead distribution assets.

### Memory/leak health

Stress testing showed:

* 96 travels;
* 48 dialogues;
* 32 menus;
* repeated GC between samples;
* heap stable;
* DOM node count stable;
* listener count stable;
* timer count stable.

Therefore, do NOT invent a memory-leak problem where none exists.

The existing refs-over-state design is working:

* `GameRuntime`: ~0 renders/sec while standing;
* ~1.2–3.5 renders/sec while walking;
* `EngineGame`: ~0 renders/sec during gameplay;
* inline runtime configuration does not cascade renders.

Other confirmed healthy mechanisms include:

* artKey gating;
* paletteKey pinning;
* DOM-cache write skipping;
* promote();
* owned timers;
* FX pooling;
* actor off-camera bounds checks;
* PlayerStudio improvements;
* DialogueBox typewriter improvements.

These existing strengths must be preserved.

# 36. Definition of Success

The modernization is successful when:

### Architecture

The engine has clear boundaries and responsibilities.

### Performance

High-frequency gameplay does not depend on React reconciliation or DOM churn.

### Extensibility

Adding a new gameplay system does not require modifying unrelated engine systems.

### Reusability

The engine can support games substantially different from the current project.

### Testability

Core systems can run independently of the browser and UI.

### Resource Management

Assets are loaded, cached, reused, and disposed predictably.

### Rendering

Rendering cost scales with visible complexity rather than unnecessary DOM representation.

### Developer Experience

A developer can understand the engine and build a new project without understanding the original game.

### Public API

Internal implementation details are not accidentally exposed as public contracts.

### Maintainability

The engine has fewer hidden dependencies, fewer special cases, and fewer game-specific assumptions.

### Performance Engineering

There are repeatable measurements and regression detection rather than subjective "it feels faster."

Treat this as a **serious engine modernization project**, not a code cleanup task.
